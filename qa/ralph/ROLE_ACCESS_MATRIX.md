# Матрица прав доступа Sporteo

Составлена из **фактического кода и фактического поведения БД**, а не из ожиданий.
Каждая строка «Нет» подтверждена живой проверкой из `qa/ralph/rls-probe.mjs`
(вход настоящим паролем → JWT роли → запрос в PostgREST). Идентификаторы
проверок указаны в колонке «Доказательство».

Дата прогона: 2026-07-31 · Организации: `qa-club-alpha`, `qa-club-beta`.

## Роли в коде

| Роль | Где задаётся | Комментарий |
|---|---|---|
| `athlete` | `users.role`, значение по умолчанию в триггере `handle_new_auth_user` | Базовая роль при регистрации |
| `coach` | `users.role` | Связь со спортсменами — `trainer_athletes` |
| `doctor` | `users.role` | Связь с пациентами — `connections(connection_type='doctor_athlete')` |
| `specialist` | `users.role` | Разрешена триггером, ролевой ассистент делит логику с доктором |
| `organization` | `users.role` | Аккаунт клуба; `organizations.id` = `users.id` этого аккаунта |
| `admin` | `users.role` | Владелец платформы / оператор внутренней CRM |
| `parent` | `parent_links`, `users.role='athlete'` + связь | Отдельной роли в `users.role` нет — родитель выражен связью |
| `trainer` | принимается триггером как синоним `coach` | Легаси-значение |

Членство в организации — `org_members(member_role: org_owner | org_admin | coach | doctor | specialist | athlete, status)`.

## Известные особенности модели

1. **`organizations.id` = `users.id` аккаунта-организации** (FK `organizations_id_fkey`).
   Один аккаунт-организация = одна карточка клуба. Строка `organizations`
   создаётся триггером при появлении пользователя с ролью `organization`.
2. **Связь врач↔пациент живёт в `connections`**, а не в отдельной таблице:
   `connection_type='doctor_athlete'`, `status='active'`, направление любое.
3. **`org_members` содержит две мёртвые политики** — `org_members_own_read`
   и `org_members_org_manage` сравнивают `users.id` с `auth.uid()`
   (разные пространства идентификаторов), поэтому не срабатывают никогда.
   Изоляцию фактически обеспечивает `org_members: org full access`.
   Дефекта доступа нет, но политики вводят в заблуждение — см. BUG_BACKLOG.
4. **RLS включён на всех 88 таблицах.** Шесть служебных таблиц
   (`ai_usage_periods`, `ai_usage_events`, `ai_audit_events`, `demo_ai_usage`,
   `telegram_deliveries`, `telegram_link_codes`) не имеют политик вовсе —
   это режим «запрещено всем, кроме service_role», доступ к ним идёт
   серверным ключом.
